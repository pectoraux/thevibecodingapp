# Master Build Prompt — Production-Grade Multi-LLM Vibe Coding Platform

You are the lead product architect, principal engineer, and implementation agent for this project.

Your task is to **design and fully build a production-grade multi-LLM software development platform** that turns a product idea/specification into a real, deployable, working software product.

This is **not** an AI chat wrapper, prompt playground, code editor, or demo.

The core product is an **AI software factory** in which multiple LLMs with different responsibilities collaborate through a controlled workflow, with GitHub as the source of truth, one frozen architecture as the governing contract, automated verification at every stage, and a final gate that proves the generated product is actually implemented rather than merely claimed to be complete.

You must inspect the existing codebase before making architectural decisions and preserve anything that is already correct and reusable.

---

# 1. Product Vision

The user should be able to do this:

1. Create a project.
2. Connect their own LLM API keys (BYOK).
3. Connect GitHub.
4. Give the system a product specification, requirements, constraints, and desired stack.
5. Have an **Architect LLM** design the complete system.
6. Have the user review and approve that architecture.
7. Freeze the architecture.
8. Press **Start Build**.
9. The platform automatically delegates work to specialized LLM agents.
10. Agents create and modify the actual repository.
11. Every meaningful change is committed to Git.
12. Multiple independent agents review the implementation.
13. A dedicated Architecture Guardian continually checks that implementation remains consistent with the frozen architecture.
14. Platform-specific implementation agents handle frontend/backend/database/mobile/cloud/etc. work.
15. Automated tests, integration tests, static analysis, security checks, runtime checks, and end-to-end tests are executed continuously.
16. Missing production credentials are detected before they become blockers.
17. The user is asked for required credentials/API keys **upfront**, including the option to use test/sandbox credentials.
18. The system continues autonomously until all defined production-readiness criteria are satisfied.
19. The user receives a real repository containing a real deployable product—not a scaffold with simulated internals.

The user should no longer need to manually copy prompts and outputs between ChatGPT, Z.ai, Claude, Gemini, etc.

The platform itself should become the orchestration layer that does that work.

---

# 2. Core Principle

The fundamental unit of the system is NOT the conversation.

It is the:

**Project → Architecture Contract → Tasks → Repository Changes → Verification → Production Readiness**

The LLMs are workers inside this system.

The platform, repository, architecture contract, task graph, test results, and verification state are the source of truth.

Do NOT allow the system to become dependent on conversational context as the primary state mechanism.

# 3. Multi-Agent Architecture

Implement the following logical agent roles.

## 3.1 Architect Agent

The Architect is responsible for designing the complete system before implementation begins.

Responsibilities:

* Understand product requirements.
* Identify functional requirements.
* Identify non-functional requirements.
* Design system architecture.
* Select technology stack.
* Define services/modules.
* Define data models.
* Define APIs.
* Define external integrations.
* Define authentication/authorization.
* Define infrastructure.
* Define deployment architecture.
* Define observability.
* Define testing strategy.
* Define security requirements.
* Define scalability assumptions.
* Define failure modes.
* Define required secrets/API keys.
* Define environment configuration.
* Define acceptance criteria.
* Identify areas where ambiguity exists.
* Identify assumptions explicitly.

The Architect must produce a formal **Architecture Contract**.

The Architecture Contract must be structured machine-readable data, not merely prose.

For example:

```text
architecture/
    architecture.json
    architecture.md
    decisions/
    contracts/
    schemas/
    api/
    infrastructure/
```

The JSON representation should contain explicit components, dependencies, interfaces, technologies, constraints, invariants, and architectural decisions.

# 4. Architecture Freeze

After the user approves the architecture, the system must allow the architecture to be **frozen**.

Once frozen:

### The architecture becomes an immutable contract.

Implementation agents MUST NOT silently change:

* technology choices
* service boundaries
* database architecture
* API contracts
* authentication model
* event architecture
* infrastructure architecture
* major dependency decisions
* data model structure
* deployment model

without an explicit architecture change process.

Implement an **Architecture Change Request** workflow.

If an implementation agent believes the architecture is insufficient, it must create:

```text
ArchitectureChangeRequest
```

containing:

* problem
* affected components
* proposed change
* rationale
* risks
* migration requirements
* affected tests
* affected APIs
* affected dependencies
* estimated implementation impact

The Architect Agent evaluates the request.

No architecture change should be considered valid until it is approved by the appropriate architecture authority.

The system must maintain:

* architecture version
* hash/version identifier
* change history
* approval history
* affected tasks
* affected files
* migration requirements

# 5. Architecture Guardian

Create a dedicated **Architecture Guardian Agent**.

This agent has a fundamentally different purpose from the Architect.

The Guardian's job is NOT to redesign the system.

Its job is to prevent architecture drift.

This distinction is critical.

The Guardian should operate with a deliberately constrained context.

It should NOT repeatedly ingest the entire project conversationally.

Instead, give it access to:

* frozen Architecture Contract
* architecture hash/version
* component dependency graph
* service boundaries
* API contracts
* database schema contracts
* coding/infrastructure constraints
* recent Git diff
* relevant changed files
* test results
* previous violations
* previous Guardian decisions

The Guardian should use targeted context retrieval rather than continually expanding context.

Its output should be structured:

```text
PASS
WARNING
VIOLATION
ARCHITECTURE_CHANGE_REQUIRED
```

A violation should include:

* violated invariant
* evidence
* files
* severity
* recommended remediation

The Guardian must NOT become another autonomous architect.

Its primary goal is preserving the frozen architecture.

# 6. Independent Code Review Agent

Create an independent **Code Review Agent**.

This agent should have a different objective from the implementation agent.

It should be skeptical and adversarial.

It should review:

* correctness
* security
* reliability
* maintainability
* edge cases
* race conditions
* error handling
* data consistency
* API correctness
* performance
* observability
* testing quality
* dependency risks
* secrets handling
* authorization
* production failure modes

The reviewer must not simply agree with generated code.

The review process should be independent whenever possible.

The reviewer receives:

* task specification
* intended behavior
* changed files
* relevant architecture contract
* test results
* previous review findings

but should NOT simply inherit the implementation agent's conclusions.

# 12. Single-LLM User

A critical product requirement:

The platform must remain useful even when the user has access to only one LLM.

Support at least three modes.

## Mode A — Multi-Key BYOK

User supplies multiple providers/models.

Use the best model for each role.

## Mode B — Single-Key Multi-Agent

The same LLM provider/model executes different logical roles.

The prompts, context, permissions, and objectives remain isolated.

For example:

```text
Architect instance
Implementation instance
Reviewer instance
Guardian instance
QA instance
```

Even if they use the same underlying model.

## Mode C — Platform-Assisted Model Pool

Where legally and technically appropriate, investigate whether the platform can provide a fallback pool of models/providers based on:

* available free tiers
* low-cost models
* open-source models
* local models
* platform-owned credits
* user-provided credentials

Do NOT implement anything that violates provider terms of service.

Create an abstraction allowing fallback routing without coupling the platform to one provider.

# 16. Production Completion Definition

This is one of the most important requirements in the entire system.

The platform must NEVER claim that a product is production-ready simply because:

* code compiles
* tests pass
* files exist
* APIs are mocked
* placeholders are present
* TODOs exist
* integrations are simulated
* fake data is being used
* functions merely return hardcoded values
* UI flows stop after frontend actions
* backend endpoints do not reach real persistence
* webhooks are not actually processed
* external services are mocked in the production path

The platform needs a formal **Production Readiness Gate**.

---

# 17. Production Readiness Gate

A product may only enter:

```text
PRODUCTION_READY
```

when all required checks pass.

At minimum check:

### Build

* application builds successfully
* production build succeeds
* dependencies resolve
* migrations succeed

### Static checks

* type checking
* linting
* static analysis
* security scanning

### Tests

* unit tests
* integration tests
* API tests
* end-to-end tests
* regression tests

### Runtime

* application starts
* health checks work
* required services connect
* database connects
* migrations work
* background jobs run
* queues work where applicable

### Integrations

* real integration paths are implemented
* credentials are configured
* test/sandbox integrations work where production credentials are unavailable
* webhooks are implemented
* webhook verification works
* retry behavior exists where necessary

### Data

* real database operations work
* persistence is real
* transactions work where necessary
* constraints are enforced
* migrations are reversible/managed appropriately

### Authentication

* login works
* logout works
* sessions/tokens work
* authorization works
* unauthorized access is blocked

### Error handling

* downstream failures are handled
* timeouts are handled
* retries exist where appropriate
* invalid input is handled
* failure states do not silently succeed

### Observability

* structured logging
* error reporting
* health checks
* useful operational metrics

### Security

* no committed secrets
* authentication reviewed
* authorization reviewed
* common injection risks checked
* dependency vulnerabilities checked
* sensitive data handling reviewed

### Configuration

* required environment variables identified
* missing configuration fails clearly
* production configuration documented

### Deployment

* reproducible deployment process exists
* deployment artifact is generated
* deployment configuration is valid
* rollback strategy exists where appropriate

# 22. Automatic Repair Loop

When verification fails, the system should automatically create a repair task.

Example:

```text
Task 41
↓
Tests fail
↓
Create repair task
↓
Implementation agent fixes issue
↓
Tests rerun
↓
Guardian
↓
Reviewer
```

Set configurable maximum retry counts.

Avoid infinite loops.

When repeated failures occur, escalate to:

```text
Human Review Required
```

with:

* failure summary
* attempted fixes
* affected files
* relevant logs
* model outputs
* proposed next action

# 45. Important Principle: Tools, Not Just Prompts

Agents need tools.

Do not build a system where every agent merely receives text and returns text.

Implement controlled tool execution.

# 47. Autonomous Build Loop

The actual autonomous loop should resemble:

```text
1. Load frozen architecture
2. Load task graph
3. Select executable task
4. Assign appropriate agent/model
5. Retrieve minimal required context
6. Execute implementation
7. Run local tests
8. Commit changes
9. Run Architecture Guardian
10. Run independent code review
11. Run integration tests
12. Mark task completed OR create repair task
13. Recompute task graph
14. Continue
15. Run production readiness gate
16. If failed, create remediation tasks
17. Continue until:
      PRODUCTION_READY
      OR HUMAN_REVIEW_REQUIRED
```

This loop is the heart of the platform.
