     1→     1→# Master Build Prompt — Production-Grade Multi-LLM Vibe Coding Platform
     2→     2→
     3→     3→You are the lead product architect, principal engineer, and implementation agent for this project.
     4→     4→
     5→     5→Your task is to **design and fully build a production-grade multi-LLM software development platform** that turns a product idea/specification into a real, deployable, working software product.
     6→     6→
     7→     7→This is **not** an AI chat wrapper, prompt playground, code editor, or demo.
     8→     8→
     9→     9→The core product is an **AI software factory** in which multiple LLMs with different responsibilities collaborate through a controlled workflow, with GitHub as the source of truth, one frozen architecture as the governing contract, automated verification at every stage, and a final gate that proves the generated product is actually implemented rather than merely claimed to be complete.
    10→    10→
    11→    11→You must inspect the existing codebase before making architectural decisions and preserve anything that is already correct and reusable.
    12→    12→
    13→    13→---
    14→    14→
    15→    15→# 1. Product Vision
    16→    16→
    17→    17→The user should be able to do this:
    18→    18→
    19→    19→1. Create a project.
    20→    20→2. Connect their own LLM API keys (BYOK).
    21→    21→3. Connect GitHub.
    22→    22→4. Give the system a product specification, requirements, constraints, and desired stack.
    23→    23→5. Have an **Architect LLM** design the complete system.
    24→    24→6. Have the user review and approve that architecture.
    25→    25→7. Freeze the architecture.
    26→    26→8. Press **Start Build**.
    27→    27→9. The platform automatically delegates work to specialized LLM agents.
    28→    28→10. Agents create and modify the actual repository.
    29→    29→11. Every meaningful change is committed to Git.
    30→    30→12. Multiple independent agents review the implementation.
    31→    31→13. A dedicated Architecture Guardian continually checks that implementation remains consistent with the frozen architecture.
    32→    32→14. Platform-specific implementation agents handle frontend/backend/database/mobile/cloud/etc. work.
    33→    33→15. Automated tests, integration tests, static analysis, security checks, runtime checks, and end-to-end tests are executed continuously.
    34→    34→16. Missing production credentials are detected before they become blockers.
    35→    35→17. The user is asked for required credentials/API keys **upfront**, including the option to use test/sandbox credentials.
    36→    36→18. The system continues autonomously until all defined production-readiness criteria are satisfied.
    37→    37→19. The user receives a real repository containing a real deployable product—not a scaffold with simulated internals.
    38→    38→
    39→    39→The user should no longer need to manually copy prompts and outputs between ChatGPT, Z.ai, Claude, Gemini, etc.
    40→    40→
    41→    41→The platform itself should become the orchestration layer that does that work.
    42→    42→
    43→    43→---
    44→    44→
    45→    45→# 2. Core Principle
    46→    46→
    47→    47→The fundamental unit of the system is NOT the conversation.
    48→    48→
    49→    49→It is the:
    50→    50→
    51→    51→**Project → Architecture Contract → Tasks → Repository Changes → Verification → Production Readiness**
    52→    52→
    53→    53→The LLMs are workers inside this system.
    54→    54→
    55→    55→The platform, repository, architecture contract, task graph, test results, and verification state are the source of truth.
    56→    56→
    57→    57→Do NOT allow the system to become dependent on conversational context as the primary state mechanism.
    58→    58→

    61→    61→# 3. Multi-Agent Architecture
    62→    62→
    63→    63→Implement the following logical agent roles.
    64→    64→
    65→    65→## 3.1 Architect Agent
    66→    66→
    67→    67→The Architect is responsible for designing the complete system before implementation begins.
    68→    68→
    69→    69→Responsibilities:
    70→    70→
    71→    71→* Understand product requirements.
    72→    72→* Identify functional requirements.
    73→    73→* Identify non-functional requirements.
    74→    74→* Design system architecture.
    75→    75→* Select technology stack.
    76→    76→* Define services/modules.
    77→    77→* Define data models.
    78→    78→* Define APIs.
    79→    79→* Define external integrations.
    80→    80→* Define authentication/authorization.
    81→    81→* Define infrastructure.
    82→    82→* Define deployment architecture.
    83→    83→* Define observability.
    84→    84→* Define testing strategy.
    85→    85→* Define security requirements.
    86→    86→* Define scalability assumptions.
    87→    87→* Define failure modes.
    88→    88→* Define required secrets/API keys.
    89→    89→* Define environment configuration.
    90→    90→* Define acceptance criteria.
    91→    91→* Identify areas where ambiguity exists.
    92→    92→* Identify assumptions explicitly.
    93→    93→
    94→    94→The Architect must produce a formal **Architecture Contract**.
    95→    95→
    96→    96→The Architecture Contract must be structured machine-readable data, not merely prose.
    97→    97→
    98→    98→For example:
    99→    99→
   100→   100→```text
   101→   101→architecture/
   102→   102→    architecture.json
   103→   103→    architecture.md
   104→   104→    decisions/
   105→   105→    contracts/
   106→   106→    schemas/
   107→   107→    api/
   108→   108→    infrastructure/
   109→   109→```
   110→   110→
   111→   111→The JSON representation should contain explicit components, dependencies, interfaces, technologies, constraints, invariants, and architectural decisions.
   112→   112→

   115→   115→# 4. Architecture Freeze
   116→   116→
   117→   117→After the user approves the architecture, the system must allow the architecture to be **frozen**.
   118→   118→
   119→   119→Once frozen:
   120→   120→
   121→   121→### The architecture becomes an immutable contract.
   122→   122→
   123→   123→Implementation agents MUST NOT silently change:
   124→   124→
   125→   125→* technology choices
   126→   126→* service boundaries
   127→   127→* database architecture
   128→   128→* API contracts
   129→   129→* authentication model
   130→   130→* event architecture
   131→   131→* infrastructure architecture
   132→   132→* major dependency decisions
   133→   133→* data model structure
   134→   134→* deployment model
   135→   135→
   136→   136→without an explicit architecture change process.
   137→   137→
   138→   138→Implement an **Architecture Change Request** workflow.
   139→   139→
   140→   140→If an implementation agent believes the architecture is insufficient, it must create:
   141→   141→
   142→   142→```text
   143→   143→ArchitectureChangeRequest
   144→   144→```
   145→   145→
   146→   146→containing:
   147→   147→
   148→   148→* problem
   149→   149→* affected components
   150→   150→* proposed change
   151→   151→* rationale
   152→   152→* risks
   153→   153→* migration requirements
   154→   154→* affected tests
   155→   155→* affected APIs
   156→   156→* affected dependencies
   157→   157→* estimated implementation impact
   158→   158→
   159→   159→The Architect Agent evaluates the request.
   160→   160→
   161→   161→No architecture change should be considered valid until it is approved by the appropriate architecture authority.
   162→   162→
   163→   163→The system must maintain:
   164→   164→
   165→   165→* architecture version
   166→   166→* hash/version identifier
   167→   167→* change history
   168→   168→* approval history
   169→   169→* affected tasks
   170→   170→* affected files
   171→   171→* migration requirements
   172→   172→
   173→   173→---
   174→   174→
   175→   175→# 5. Architecture Guardian
   176→   176→
   177→   177→Create a dedicated **Architecture Guardian Agent**.
   178→   178→
   179→   179→This agent has a fundamentally different purpose from the Architect.
   180→   180→
   181→   181→The Guardian's job is NOT to redesign the system.
   182→   182→
   183→   183→Its job is to prevent architecture drift.
   184→   184→
   185→   185→This distinction is critical.
   186→   186→
   187→   187→The Guardian should operate with a deliberately constrained context.
   188→   188→
   189→   189→It should NOT repeatedly ingest the entire project conversationally.
   190→   190→
   191→   191→Instead, give it access to:
   192→   192→
   193→   193→* frozen Architecture Contract
   194→   194→* architecture hash/version
   195→   195→* component dependency graph
   196→   196→* service boundaries
   197→   197→* API contracts
   198→   198→* database schema contracts
   199→   199→* coding/infrastructure constraints
   200→   200→* recent Git diff
   201→   201→* relevant changed files
   202→   202→* test results
   203→   203→* previous violations
   204→   204→* previous Guardian decisions
   205→   205→
   206→   206→The Guardian should use targeted context retrieval rather than continually expanding context.
   207→   207→
   208→   208→Its output should be structured:
   209→   209→
   210→   210→```text
   211→   211→PASS
   212→   212→WARNING
   213→   213→VIOLATION
   214→   214→ARCHITECTURE_CHANGE_REQUIRED
   215→   215→```
   216→   216→
   217→   217→A violation should include:
   218→   218→
   219→   219→* violated invariant
   220→   220→* evidence
   221→   221→* files
   222→   222→* severity
   223→   223→* recommended remediation
   224→   224→
   225→   225→The Guardian must NOT become another autonomous architect.
   226→   226→
   227→   227→Its primary goal is preserving the frozen architecture.
   228→   228→

   235→   235→This agent should have a different objective from the implementation agent.
   236→   236→
   237→   237→It should be skeptical and adversarial.
   238→   238→
   239→   239→It should review:
   240→   240→
   241→   241→* correctness
   242→   242→* security
   243→   243→* reliability
   244→   244→* maintainability
   245→   245→* edge cases
   246→   246→* race conditions
   247→   247→* error handling
   248→   248→* data consistency
   249→   249→* API correctness
   250→   250→* performance
   251→   251→* observability
   252→   252→* testing quality
   253→   253→* dependency risks
   254→   254→* secrets handling
   255→   255→* authorization
   256→   256→* production failure modes
   257→   257→
   258→   258→The reviewer must not simply agree with generated code.
   259→   259→
   260→   260→The review process should be independent whenever possible.
   261→   261→
   262→   262→The reviewer receives:
   263→   263→
   264→   264→* task specification
   265→   265→* intended behavior
   266→   266→* changed files
   267→   267→* relevant architecture contract
   268→   268→* test results
   269→   269→* previous review findings
   270→   270→
   271→   271→but should NOT simply inherit the implementation agent's conclusions.

   374→   374→
   375→   375→Build an actual orchestration engine.

   377→   377→The system should convert the Architecture Contract into a **Task Graph**.
   378→   378→
   379→   379→A task should have:
   380→   380→
   381→   381→```text
   382→   382→id
   383→   383→title
   384→   384→description
   385→   385→component
   386→   386→dependencies
   387→   387→inputs
   388→   388→outputs
   389→   389→acceptanceCriteria
   390→   390→requiredTests
   391→   391→agentType
   392→   392→priority
   393→   393→risk
   394→   394→status
   395→   395→attempts
   396→   396→assignedModel
   397→   397→reviewStatus
   398→   398→architectureStatus
   399→   399→```
   400→   400→
   401→   401→Support dependency-aware execution.
   402→   402→
   403→   403→Example:
   404→   404→
   405→   405→```text
   406→   406→database schema
   407→   407→       ↓
   408→   408→backend API
   409→   409→       ↓
   410→   410→frontend integration
   411→   411→       ↓
   412→   412→end-to-end tests
   413→   413→```
   414→   414→
   415→   415→The system must not ask multiple agents to blindly modify the same part of the codebase simultaneously.
   416→   416→
   417→   417→Implement repository locking / task-level ownership where necessary.

   455→   455→

   471→   471→
   472→   472→The user must control their own LLM provider credentials.
   473→   473→
   474→   474→Support multiple providers.
   475→   475→
   476→   476→The system should use a provider abstraction such as:
   477→   477→
   478→   478→```text
   479→   479→LLMProvider
   480→   480→    provider
   481→   481→    model
   482→   482→    credentials
   483→   483→    capabilities
   484→   484→    contextWindow
   485→   485→    pricing
   486→   486→    rateLimits
   487→   487→    reliability
   488→   488→```
   489→   489→
   490→   490→Do not hard-code the orchestration engine around a single model provider.
   491→   491→
   492→   492→The system should support assigning different models to different roles.
   493→   493→
   494→   494→Example:
   495→   495→
   496→   496→```text
   497→   497→Architect        → Model A
   498→   498→Implementation   → Model B

   500→   500→Code Review      → Model D

   504→   504→Users should be able to override model assignments.
   505→   505→

   509→   509→
   510→   510→Do not simply select models by name.
   511→   511→
   512→   512→Define model capabilities.
   513→   513→
   514→   514→For example:
   515→   515→
   516→   516→```text

   518→   518→reasoning
   519→   519→architecture

   521→   521→vision

   524→   524→cost
   525→   525→context_window
   526→   526→structured_output
   527→   527→```
   528→   528→
   529→   529→A task should request capabilities.
   530→   530→
   531→   531→The router chooses an appropriate model.
   532→   532→
   533→   533→Example:
   534→   534→
   535→   535→```text

   537→   537→"Review database migration for data-integrity failures"

   540→   540→- coding

   549→   549→# 12. Single-LLM User
   550→   550→
   551→   551→A critical product requirement:
   552→   552→
   553→   553→The platform must remain useful even when the user has access to only one LLM.
   554→   554→
   555→   555→Support at least three modes.
   556→   556→
   557→   557→## Mode A — Multi-Key BYOK
   558→   558→
   559→   559→User supplies multiple providers/models.
   560→   560→
   561→   561→Use the best model for each role.
   562→   562→
   563→   563→## Mode B — Single-Key Multi-Agent
   564→   564→
   565→   565→The same LLM provider/model executes different logical roles.
   566→   566→
   567→   567→The prompts, context, permissions, and objectives remain isolated.
   568→   568→
   569→   569→For example:
   570→   570→
   571→   571→```text
   572→   572→Architect instance
   573→   573→Implementation instance
   574→   574→Reviewer instance
   575→   575→Guardian instance
   576→   576→QA instance
   577→   577→```
   578→   578→
   579→   579→Even if they use the same underlying model.
   580→   580→
   581→   581→## Mode C — Platform-Assisted Model Pool
   582→   582→
   583→   583→Where legally and technically appropriate, investigate whether the platform can provide a fallback pool of models/providers based on:
   584→   584→
   585→   585→* available free tiers
   586→   586→* low-cost models
   587→   587→* open-source models
   588→   588→* local models
   589→   589→* platform-owned credits
   590→   590→* user-provided credentials
   591→   591→
   592→   592→Do NOT implement anything that violates provider terms of service.
   593→   593→
   594→   594→Create an abstraction allowing fallback routing without coupling the platform to one provider.
   595→   595→

   619→   619→Each agent receives only the context required for its responsibility.
   620→   620→
   621→   621→The Architecture Guardian should have especially strict context limits.
   622→   622→
   623→   623→Its canonical inputs should be:
   624→   624→
   625→   625→```text

   628→   628→Relevant dependency graph

   639→   639→not the entire conversation.
   640→   640→

   739→   739→# 16. Production Completion Definition
   740→   740→
   741→   741→This is one of the most important requirements in the entire system.
   742→   742→
   743→   743→The platform must NEVER claim that a product is production-ready simply because:
   744→   744→
   745→   745→* code compiles
   746→   746→* tests pass
   747→   747→* files exist
   748→   748→* APIs are mocked
   749→   749→* placeholders are present
   750→   750→* TODOs exist
   751→   751→* integrations are simulated
   752→   752→* fake data is being used
   753→   753→* functions merely return hardcoded values
   754→   754→* UI flows stop after frontend actions
   755→   755→* backend endpoints do not reach real persistence
   756→   756→* webhooks are not actually processed
   757→   757→* external services are mocked in the production path
   758→   758→
   759→   759→The platform needs a formal **Production Readiness Gate**.

   871→   871→# 18. Fake / Placeholder Detection
   872→   872→
   873→   873→Implement an automated **Fake Implementation Detector**.
   874→   874→
   875→   875→Search the repository for suspicious patterns including:
   876→   876→
   877→   877→```text
   878→   878→TODO
   879→   879→FIXME
   880→   880→coming soon
   881→   881→not implemented
   882→   882→placeholder
   883→   883→mock
   884→   884→stub
   885→   885→dummy
   886→   886→fake
   887→   887→temporary
   888→   888→hardcoded response
   889→   889→return true
   890→   890→return false
   891→   891→return []
   892→   892→return {}
   893→   893→console.log
   894→   894→pass
   895→   895→throw new Error("not implemented")
   896→   896→```
   897→   897→
   898→   898→Do not blindly reject legitimate occurrences.
   899→   899→
   900→   900→The detector should classify them and require review where they occur in production paths.
   901→   901→
   902→   902→Also detect:
   903→   903→
   904→   904→* frontend calling fake APIs
   905→   905→* API endpoints returning static values
   906→   906→* mock services accidentally enabled in production
   907→   907→* databases never queried
   908→   908→* integrations with no network calls
   909→   909→* generated example data presented as real data
   910→   910→* code paths never wired into application execution
   911→   911→

  1673→  1673→

  1684→  1684→create_pull_request
  1685→  1685→inspect_logs

  1687→  1687→run_browser_test

  1690→  1690→
  1691→  1691→Tool permissions should be role-specific.
  1692→  1692→

  1694→  1694→

  1696→  1696→

  1736→  1736→

  1739→  1739→```text

  1743→  1743→4. Assign appropriate agent/model
  1744→  1744→5. Retrieve minimal required context
  1745→  1745→6. Execute implementation
  1746→  1746→7. Run local tests
  1747→  1747→8. Commit changes
  1748→  1748→9. Run Architecture Guardian
  1749→  1749→10. Run independent code review
  1750→  1750→11. Run integration tests
  1751→  1751→12. Mark task completed OR create repair task
  1752→  1752→13. Recompute task graph
  1753→  1753→14. Continue
  1754→  1754→15. Run production readiness gate
  1755→  1755→16. If failed, create remediation tasks
  1756→  1756→17. Continue until:
  1757→  1757→      PRODUCTION_READY
  1758→  1758→      OR HUMAN_REVIEW_REQUIRED
