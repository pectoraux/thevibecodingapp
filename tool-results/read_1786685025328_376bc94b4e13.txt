     1→# Master Build Prompt — Production-Grade Multi-LLM Vibe Coding Platform
     2→
     3→You are the lead product architect, principal engineer, and implementation agent for this project.
     4→
     5→Your task is to **design and fully build a production-grade multi-LLM software development platform** that turns a product idea/specification into a real, deployable, working software product.
     6→
     7→This is **not** an AI chat wrapper, prompt playground, code editor, or demo.
     8→
     9→The core product is an **AI software factory** in which multiple LLMs with different responsibilities collaborate through a controlled workflow, with GitHub as the source of truth, one frozen architecture as the governing contract, automated verification at every stage, and a final gate that proves the generated product is actually implemented rather than merely claimed to be complete.
    10→
    11→You must inspect the existing codebase before making architectural decisions and preserve anything that is already correct and reusable.
    12→
    13→---
    14→
    15→# 1. Product Vision
    16→
    17→The user should be able to do this:
    18→
    19→1. Create a project.
    20→2. Connect their own LLM API keys (BYOK).
    21→3. Connect GitHub.
    22→4. Give the system a product specification, requirements, constraints, and desired stack.
    23→5. Have an **Architect LLM** design the complete system.
    24→6. Have the user review and approve that architecture.
    25→7. Freeze the architecture.
    26→8. Press **Start Build**.
    27→9. The platform automatically delegates work to specialized LLM agents.
    28→10. Agents create and modify the actual repository.
    29→11. Every meaningful change is committed to Git.
    30→12. Multiple independent agents review the implementation.
    31→13. A dedicated Architecture Guardian continually checks that implementation remains consistent with the frozen architecture.
    32→14. Platform-specific implementation agents handle frontend/backend/database/mobile/cloud/etc. work.
    33→15. Automated tests, integration tests, static analysis, security checks, runtime checks, and end-to-end tests are executed continuously.
    34→16. Missing production credentials are detected before they become blockers.
    35→17. The user is asked for required credentials/API keys **upfront**, including the option to use test/sandbox credentials.
    36→18. The system continues autonomously until all defined production-readiness criteria are satisfied.
    37→19. The user receives a real repository containing a real deployable product—not a scaffold with simulated internals.
    38→
    39→The user should no longer need to manually copy prompts and outputs between ChatGPT, Z.ai, Claude, Gemini, etc.
    40→
    41→The platform itself should become the orchestration layer that does that work.
    42→
    43→---
    44→
    45→# 2. Core Principle
    46→
    47→The fundamental unit of the system is NOT the conversation.
    48→
    49→It is the:
    50→
    51→**Project → Architecture Contract → Tasks → Repository Changes → Verification → Production Readiness**
    52→
    53→The LLMs are workers inside this system.
    54→
    55→The platform, repository, architecture contract, task graph, test results, and verification state are the source of truth.
    56→
    57→Do NOT allow the system to become dependent on conversational context as the primary state mechanism.
    58→

    61→# 3. Multi-Agent Architecture
    62→
    63→Implement the following logical agent roles.
    64→
    65→## 3.1 Architect Agent
    66→
    67→The Architect is responsible for designing the complete system before implementation begins.
    68→
    69→Responsibilities:
    70→
    71→* Understand product requirements.
    72→* Identify functional requirements.
    73→* Identify non-functional requirements.
    74→* Design system architecture.
    75→* Select technology stack.
    76→* Define services/modules.
    77→* Define data models.
    78→* Define APIs.
    79→* Define external integrations.
    80→* Define authentication/authorization.
    81→* Define infrastructure.
    82→* Define deployment architecture.
    83→* Define observability.
    84→* Define testing strategy.
    85→* Define security requirements.
    86→* Define scalability assumptions.
    87→* Define failure modes.
    88→* Define required secrets/API keys.
    89→* Define environment configuration.
    90→* Define acceptance criteria.
    91→* Identify areas where ambiguity exists.
    92→* Identify assumptions explicitly.
    93→
    94→The Architect must produce a formal **Architecture Contract**.
    95→
    96→The Architecture Contract must be structured machine-readable data, not merely prose.
    97→
    98→For example:
    99→
   100→```text
   101→architecture/
   102→    architecture.json
   103→    architecture.md
   104→    decisions/
   105→    contracts/
   106→    schemas/
   107→    api/
   108→    infrastructure/
   109→```
   110→
   111→The JSON representation should contain explicit components, dependencies, interfaces, technologies, constraints, invariants, and architectural decisions.

   115→# 4. Architecture Freeze
   116→
   117→After the user approves the architecture, the system must allow the architecture to be **frozen**.
   118→
   119→Once frozen:
   120→
   121→### The architecture becomes an immutable contract.
   122→
   123→Implementation agents MUST NOT silently change:
   124→
   125→* technology choices
   126→* service boundaries
   127→* database architecture
   128→* API contracts
   129→* authentication model
   130→* event architecture
   131→* infrastructure architecture
   132→* major dependency decisions
   133→* data model structure
   134→* deployment model
   135→
   136→without an explicit architecture change process.
   137→
   138→Implement an **Architecture Change Request** workflow.
   139→
   140→If an implementation agent believes the architecture is insufficient, it must create:
   141→
   142→```text
   143→ArchitectureChangeRequest
   144→```
   145→
   146→containing:
   147→
   148→* problem
   149→* affected components
   150→* proposed change
   151→* rationale
   152→* risks
   153→* migration requirements
   154→* affected tests
   155→* affected APIs
   156→* affected dependencies
   157→* estimated implementation impact
   158→
   159→The Architect Agent evaluates the request.
   160→
   161→No architecture change should be considered valid until it is approved by the appropriate architecture authority.
   162→
   163→The system must maintain:
   164→
   165→* architecture version
   166→* hash/version identifier
   167→* change history
   168→* approval history
   169→* affected tasks
   170→* affected files
   171→* migration requirements
   172→

   175→# 5. Architecture Guardian
   176→
   177→Create a dedicated **Architecture Guardian Agent**.
   178→
   179→This agent has a fundamentally different purpose from the Architect.
   180→
   181→The Guardian's job is NOT to redesign the system.
   182→
   183→Its job is to prevent architecture drift.
   184→
   185→This distinction is critical.
   186→
   187→The Guardian should operate with a deliberately constrained context.
   188→
   189→It should NOT repeatedly ingest the entire project conversationally.
   190→
   191→Instead, give it access to:
   192→
   193→* frozen Architecture Contract
   194→* architecture hash/version
   195→* component dependency graph
   196→* service boundaries
   197→* API contracts
   198→* database schema contracts
   199→* coding/infrastructure constraints
   200→* recent Git diff
   201→* relevant changed files
   202→* test results
   203→* previous violations
   204→* previous Guardian decisions
   205→
   206→The Guardian should use targeted context retrieval rather than continually expanding context.
   207→
   208→Its output should be structured:
   209→
   210→```text
   211→PASS
   212→WARNING
   213→VIOLATION
   214→ARCHITECTURE_CHANGE_REQUIRED
   215→```
   216→
   217→A violation should include:
   218→
   219→* violated invariant
   220→* evidence
   221→* files
   222→* severity
   223→* recommended remediation
   224→
   225→The Guardian must NOT become another autonomous architect.
   226→
   227→Its primary goal is preserving the frozen architecture.
   228→

   235→This agent should have a different objective from the implementation agent.
   236→
   237→It should be skeptical and adversarial.
   238→
   239→It should review:
   240→
   241→* correctness
   242→* security
   243→* reliability
   244→* maintainability
   245→* edge cases
   246→* race conditions
   247→* error handling
   248→* data consistency
   249→* API correctness
   250→* performance
   251→* observability
   252→* testing quality
   253→* dependency risks
   254→* secrets handling
   255→* authorization
   256→* production failure modes
   257→
   258→The reviewer must not simply agree with generated code.
   259→
   260→The review process should be independent whenever possible.
   261→
   262→The reviewer receives:
   263→
   264→* task specification
   265→* intended behavior
   266→* changed files
   267→* relevant architecture contract
   268→* test results
   269→* previous review findings
   270→
   271→but should NOT simply inherit the implementation agent's conclusions.

   471→
   472→The user must control their own LLM provider credentials.

   475→

   477→
   478→```text

   483→    capabilities

   490→Do not hard-code the orchestration engine around a single model provider.

   492→The system should support assigning different models to different roles.
   493→
   494→Example:
   495→
   496→```text

   509→
   510→Do not simply select models by name.
   511→
   512→Define model capabilities.
   513→
   514→For example:
   515→
   516→```text
   517→coding
   518→reasoning
   519→architecture

   522→tool_use

   524→cost

   529→A task should request capabilities.
   530→
   531→The router chooses an appropriate model.

   533→Example:
   534→
   535→```text

   537→"Review database migration for data-integrity failures"

   540→- coding

   542→- structured_output

   549→# 12. Single-LLM User
   550→
   551→A critical product requirement:
   552→
   553→The platform must remain useful even when the user has access to only one LLM.
   554→
   555→Support at least three modes.
   556→
   557→## Mode A — Multi-Key BYOK
   558→
   559→User supplies multiple providers/models.
   560→
   561→Use the best model for each role.
   562→
   563→## Mode B — Single-Key Multi-Agent
   564→
   565→The same LLM provider/model executes different logical roles.
   566→
   567→The prompts, context, permissions, and objectives remain isolated.
   568→
   569→For example:
   570→
   571→```text
   572→Architect instance
   573→Implementation instance
   574→Reviewer instance
   575→Guardian instance
   576→QA instance
   577→```
   578→
   579→Even if they use the same underlying model.
   580→
   581→## Mode C — Platform-Assisted Model Pool
   582→
   583→Where legally and technically appropriate, investigate whether the platform can provide a fallback pool of models/providers based on:
   584→
   585→* available free tiers
   586→* low-cost models
   587→* open-source models
   588→* local models
   589→* platform-owned credits
   590→* user-provided credentials
   591→
   592→Do NOT implement anything that violates provider terms of service.
   593→
   594→Create an abstraction allowing fallback routing without coupling the platform to one provider.

   624→
   625→```text

   739→# 16. Production Completion Definition
   740→
   741→This is one of the most important requirements in the entire system.
   742→
   743→The platform must NEVER claim that a product is production-ready simply because:
   744→
   745→* code compiles
   746→* tests pass
   747→* files exist
   748→* APIs are mocked
   749→* placeholders are present
   750→* TODOs exist
   751→* integrations are simulated
   752→* fake data is being used
   753→* functions merely return hardcoded values
   754→* UI flows stop after frontend actions
   755→* backend endpoints do not reach real persistence
   756→* webhooks are not actually processed
   757→* external services are mocked in the production path
   758→
   759→The platform needs a formal **Production Readiness Gate**.

   871→# 18. Fake / Placeholder Detection
   872→
   873→Implement an automated **Fake Implementation Detector**.
   874→
   875→Search the repository for suspicious patterns including:
   876→
   877→```text
   878→TODO
   879→FIXME
   880→coming soon
   881→not implemented
   882→placeholder
   883→mock
   884→stub
   885→dummy
   886→fake
   887→temporary
   888→hardcoded response
   889→return true
   890→return false
   891→return []
   892→return {}
   893→console.log
   894→pass
   895→throw new Error("not implemented")
   896→```
   897→
   898→Do not blindly reject legitimate occurrences.
   899→
   900→The detector should classify them and require review where they occur in production paths.
   901→
   902→Also detect:
   903→
   904→* frontend calling fake APIs
   905→* API endpoints returning static values
   906→* mock services accidentally enabled in production
   907→* databases never queried
   908→* integrations with no network calls
   909→* generated example data presented as real data
   910→* code paths never wired into application execution

   928→Commit
   929→Tests executed
   930→Test results
   931→Review results
   932→Guardian result
   933→Architecture version
   934→```
   935→
   936→The platform should be able to answer:
   937→
   938→> "Why does the system believe this feature is complete?"
   939→
   940→The answer must be based on evidence, not an LLM assertion.
   941→

   943→
   944→# 20. No "Trust Me" Completion
   945→
   946→LLMs are not authoritative about whether they have completed a task.
   947→
   948→An LLM may say:
   949→
   950→> "The Stripe integration is fully implemented."
   951→
   952→The platform should respond by checking:
   953→
   954→* required SDK dependency
   955→* configuration
   956→* real API invocation
   957→* webhook endpoint
   958→* webhook signature verification
   959→* persistence
   960→* error handling
   961→* tests
   962→* environment configuration
   963→* actual execution
   964→
   965→Only evidence can transition a task into completed state.
   966→
   967→---
   968→
   969→# 21. Verification Layers
   970→
   971→Implement multiple independent verification layers:
   972→
   973→```text
   974→Implementation Agent
   975→        ↓
   976→Tests
   977→        ↓
   978→Architecture Guardian
   979→        ↓
   980→Independent Code Review
   981→        ↓
   982→Integration Verification
   983→        ↓
   984→Production Readiness Gate
   985→```
   986→
   987→Do not allow the same agent to both implement and certify its own work wherever avoidable.
   988→

   991→# 22. Automatic Repair Loop
   992→
   993→When verification fails, the system should automatically create a repair task.
   994→
   995→Example:
   996→
   997→```text
   998→Task 41
   999→↓
  1000→Tests fail
  1001→↓
  1002→Create repair task
  1003→↓
  1004→Implementation agent fixes issue
  1005→↓
  1006→Tests rerun
  1007→↓
  1008→Guardian
  1009→↓
  1010→Reviewer
  1011→```
  1012→
  1013→Set configurable maximum retry counts.
  1014→
  1015→Avoid infinite loops.
  1016→
  1017→When repeated failures occur, escalate to:
  1018→
  1019→```text
  1020→Human Review Required
  1021→```
  1022→
  1023→with:
  1024→
  1025→* failure summary
  1026→* attempted fixes
  1027→* affected files
  1028→* relevant logs
  1029→* model outputs
  1030→* proposed next action
